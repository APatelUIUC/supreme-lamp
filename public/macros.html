Macros: a food log you talk to — and the engineering loop behind it

A production, multi-tenant nutrition tracker whose primary interface is conversation — log meals from claude.ai or ChatGPT through an MCP connector, or a PWA when you'd rather tap. Built solo, benchmark-first, with Claude as both the product's engine and the engineering partner. This is the story of the decisions, with the measurements that made them.

The problem

Food tracking works — adherence is the single best predictor of outcomes — and almost nobody sustains it, because logging is miserable. Database search, portion pickers, five taps per meal. Category 30-day retention runs 8–14%. The bet: the interface should be a sentence. "Log the chicken burrito bowl and a coke zero" — and an assistant that already knows your usual meals does the rest. Two numbers only (calories and protein) by design; the rest is stored but never in your face.

That bet only works if three hard things hold: the estimates have to be good enough to trust, the marginal cost of AI has to survive a free product, and the conversational surface has to be a first-class production citizen — not a demo bolted to a database.

The system

One codebase, three surfaces

      (read-only)                │  and user_id is the mandatory first argument everywhere
                                 ▼
                          Neon Postgres (always-on, same region)

Details that carry the weight: an identities table maps multiple providers to one person, so signing in with Google on the web and authorizing claude.ai's connector resolve to the same account. Cross-user isolation is structural — every storage function takes user_id first with no default, so a forgotten argument is a TypeError, not a data leak — and a dedicated test suite pins it. Households share exactly one thing (a saved-meal library), asserted by a test that enumerates what must not cross the boundary.

The eval loop — where the architecture came from

Instead of picking a model and prompting until it felt right, I benchmarked six backends on 150 human-verified meals from NutriBench (stratified: half with explicit gram weights, half colloquial like "a bowl of rice"), identical prompt and schema everywhere.

Backendenergy MAPEwithin 20%carb acc @7.5g$/user/mo
Apple on-device (3B)84.7%26.7%26.7%0
Apple PCC (server)29.3%56.7%53.3%0
Claude Haiku 4.545.5%47.0%50.3%0.091
Claude Sonnet 534.2%65.1%64.4%0.823
Claude Opus 521.1%72.7%72.7%1.266

Three findings did real architectural work:

  1. Models know nutrition; they cannot guess portions. With explicit grams, frontier models land ~11% MAPE; take the grams away and error triples. So the product invests in getting quantity — favorites, "how big was the bowl?", countable units — rather than in bigger models. A model upgrade buys +14 points on colloquial input; the user saying "2 cups" buys ~35.
  2. Structure beats prose. Forcing the model to emit a component parse — {name, grams, per-100g values} — and summing in code matched chain-of-thought accuracy while cutting bias from −30 kcal to +4 and running 20% faster. That parse then became the product: it's the correction UI (fix one component, not the whole guess) and the seed of each user's personal food table. One correction makes a brand food exact forever.
  3. The cost frontier is the business model. At measured token counts, Haiku serves a free tier at $0.091/user/month — ~1,100 users per $100 — while Opus's 72.7% carb accuracy (above NutriBench's published GPT-4o + CoT best) prices a paid "precision" tier. And Apple's Private Cloud Compute, benchmarked the day macOS 27 made it testable, lands Sonnet-class at $0 — the long-term free-tier engine for eligible devices, with the server path kept behind a feature flag as insurance.

Production, honestly

The connector is in daily use — real meals, real corrections, my own household as the first tenants. Four bugs only production could teach, each now a regression test that was verified to fail without its fix: serverless froze function instances while Neon closed their pooled sockets (dead-connection handouts); FastMCP's OAuth discovery routes only work mounted at root, last; a provider default collided two OAuth callbacks on one path; and an auth library never set the field every example reads, so tool listing worked while every tool call failed "not authenticated" — the connector looked healthy and only invocations broke.

The latency investigation

Preparing for outside users, I measured the first-touch path: 4.48s after any idle period, 0.09s warm. Conventional wisdom says "serverless cold start — re-platform." Measuring the layers said otherwise:

ConfigurationFirst touch after idle
Baseline (Hobby plan, DB scale-to-zero)4.48–4.73s
+ warm function instance (config)1.08s
+ always-on DB compute (config)0.25–0.36s, verified across three idle windows

The function runtime owned 3.6 of the 4.5 seconds — not the database everyone blames. Both fixes were configuration; the re-platform I'd sketched was declined as timeline risk for $10/month of savings. ~15× p95 improvement, zero code changed. Knowing when not to migrate is also an engineering deliverable.

What opening it up made me check

Publishing the repo and inviting strangers warranted an audit rather than a vibe. It found three things. There was no rate limiting anywhere — and inference costs real money per call, so the most likely incident needed no malice at all, just a loop; that's now a per-user limit held in the database, because in-memory counters are meaningless on serverless where each instance keeps its own count. There was a validation asymmetry: the web API enforced value bounds through its request models while the connector, which has no such models, accepted anything — a second entry point had silently voided the first one's validation, so bounds moved to the single storage layer both doors share. And user-typed meal descriptions flow into the nightly agent's context, which is a prompt-injection surface; the defense that matters there isn't the wording of a prompt, it's that the agent's database session is read-only at connect time and its output is a report rather than an action. THREAT_MODEL.md carries the rest, including a section on what is deliberately not defended.

The behavior layer: five hypotheses, one survivor

Estimation quality is only half the product; the other half is whether an assistant holding these tools behaves — looks up before guessing, edits instead of re-logging, asks at most one question. So the connector got its own eval: 16 conversational cases across 8 behavior families, run as real Agent SDK sessions against in-process replicas of the production tools, graded deterministically on tool-call patterns and database end-state, three repetitions per claim, stable case ids so comparisons report per-case flips rather than aggregate scores.

Two instrument bugs surfaced and were caught by the eval itself: harness tool schemas that quietly marked optional parameters required (inducing error-retry "duplicates" production never sees), and a judge grading conversations without sight of the user's turns. And the intervention that beat every prompt variant wasn't a prompt at all: a deterministic idempotency guard in the storage layer — identical inserts within 90 seconds collapse — which also closed a duplicate-entry class the nightly auditor had already flagged in real production data. Four of five hypotheses died in the data, including two of mine. That's the point of having data.

The agentic layer

A nightly auditor built on the Claude Agent SDK reviews the last week of data — structurally read-only (the Postgres session is pinned read_only at connection time; the agent cannot write, it can only propose). Its first two nights earned their place in this page:

  • Night one, the pipeline broke — Neon's pooler rejects the read-only startup parameter. The agent's report opened: "Both data sources are unreachable — this isn't something a retry will fix, so I'm stopping rather than fabricate a report," followed by the correct root-cause diagnosis and the fix (use the unpooled DSN, same reason pg_dump does). An auditor that invents plausible numbers when its pipeline fails is worse than none.
  • Night two, I was the one corrected. The auditor's textbook integrity check (calories ≈ 4·carbs + 4·protein + 9·fat) flagged five entries that were perfectly valid — because this is deliberately a two-number product where carbs and fat may be honestly zero. Generic data-quality rules had encoded someone else's schema. The checks were rewritten around the product's semantics (protein×4 can never exceed calories; full-macro arithmetic only when the user specified everything), and the next run flagged exactly one thing: a genuine double-logged entry.

That arc — generic rule, domain pushback, semantics encoded, clean signal — is the whole thesis of AI implementation work, compressed into two nightly reports and about forty cents of inference.

The coaching behavior itself ships as a versioned skill (skills/macros-coach/): look up favorites before estimating, parse components before summing, ask at most one clarifying question, treat corrections as data. Every rule cites the eval that justified it.

Built to stay safe to change

Every change described here landed while the system stayed in production, serving its users — including a database migration, a front-end rewrite, and a hosting reconfiguration. That isn't nerve; it's the assets underneath: a benchmark sample with stable row ids so any model change can be compared per-case, a behavior suite that catches connector regressions, regression tests written to fail without their fix, a cross-user isolation suite that fails loudly on a forgotten argument, and post-mortems that keep solved problems solved. Those are what make a change cheap, and they're the part of this I'd bring to someone else's codebase first.

The reading behind the decisions

Every load-bearing decision above leaned on something read first. The honest list, mapped to what it changed:

  • NutriBench v2 — arXiv:2407.12843, 15,617 human-verified meal descriptions with macro labels. Supplied the 150-row stable-id benchmark sample and the metric/colloquial split that produced the central finding — models know nutrition facts but cannot guess portions — and its published GPT-4o + CoT baseline is the external reference point the results are compared against.
  • Apple's Foundation Models & Private Cloud Compute documentation — the availability/quota APIs and the generation-time entitlement gating (com.apple.developer.private-cloud-compute), verified empirically rather than assumed. This reading plus the PCC benchmark set the free-tier model ladder: PCC where entitled, Haiku 4.5 everywhere else.
  • TwoMillionKit — insidegui/TwoMillionKit, which documents the macOS fm CLI mechanism that made benchmarking PCC locally possible at all before any entitlement exists.
  • The MCP specification and its auth stack — the Model Context Protocol spec, OAuth 2.1, and RFC 7591 dynamic client registration. These are why the connector works in claude.ai and ChatGPT with a URL and zero manual credentials.
  • Ode's engineering writing — Stop Designing Chatbots, their posts on eval-driven development and the "Rotten Tomatoes problem" in evals, Using MCPs with Evals, and Eddie Siegel on deterministic checks plus secondary verification. Read early, and visible in the result: this app deliberately has no chat window, the behavior suite reports per-case flip tables rather than a single score, and the estimator's totals are summed in code the model never touches.

Method: overusing the tools, on purpose

This was built solo, with Claude Code as the engineering partner throughout — the evals, the agents, the migrations, and most of the code were produced in that loop, including the parts where Claude's own proposals (an instruction rewrite, a re-platform) were tested and rejected on evidence. Working this way is a skill with a shape: decompose to where measurement can steer, keep the human on the decisions data can't make, and never ship the model's confidence without a check the model can't fake. The system being about Claude while being built with Claude wasn't a gimmick; it's how one engineer covers benchmark science, infrastructure, agent design, and a front-end redesign at all — and it's the working style I'd bring to a team.
